# Run 0017 - distribution-regen-aws-on-ci

Run of wave 003 (workdir-generation-hardening), manifest id W-4, phase P2.

## Scope

Get `distribution/aws` regenerated by the `package-builder.yaml` GitHub Action from branch
`wave-003`, so the committed AWS bootstrap carries the nine family colours that W-3 added to
`source/library/packages/aws/families.csv`, without any local container render. The run pushes
the branch, dispatches the Action once for `pkgName=aws`, waits for its three jobs, and fast-forwards
the local branch onto the commit that its last job (`push-distribution`) pushed.

In scope: `git push origin wave-003` (a fast-forward of the commits W-1 to W-3 made), one
`gh workflow run package-builder.yaml --ref wave-003 -f pkgName=aws`, read-only `gh run` calls, and
`git pull --ff-only`. If the render fails, the failure policy of the wave's Autonomy Contract
(`DEC-5`) allows one more dispatch, preceded when the log points at a file this wave owns by a fix
committed in the owning P1 run.

Out of scope, and the authorisation recorded in `prg-003` (2026-11-07, "Oui, dans ce périmètre")
does not cover them: `master`, any tag, `npm run release`, any package other than `aws`, any other
workflow, any push other than `wave-003`, a third dispatch, a force push, a local Podman or
`generate:package` build, and hand-made commits under `distribution/` (the Action commits by itself).
No file is edited by this run except its own documents.

## Decisions

- `DEC-1` Push first, then dispatch, from this worktree, only after a pre-flight (`T-1`): the current
  branch is `wave-003`; `git fetch origin wave-003` shows `origin/wave-003` is an ancestor of `HEAD`;
  `git status --short -- source scripts test doc .github package.json package-lock.json` is empty (the
  pushed tree is the one the P1 gate verified); and the `prg-003` authorisation line is present. If any
  check fails, nothing is pushed and the run stops `blocked` with the reason. Rejected: dispatching
  before the push (the Action builds the remote tip, which would lack W-1 to W-3), and pushing with
  `--force` (the history is a fast-forward, a force would only matter if it were not).
- `DEC-2` One dispatch, identified from the repository's own data, not from `gh` output alone: after
  `gh workflow run`, list `gh run list --workflow package-builder.yaml --branch wave-003 --event
  workflow_dispatch --json databaseId,headSha,createdAt,status` and take the run whose `headSha` equals
  the pushed tip (there is none before this dispatch, so the match is unique). Retry the listing for up to
  2 minutes, as a run takes a few seconds to appear. Rejected: taking "the latest run", which could be a
  run of another ref.
- `DEC-3` No commit on local `wave-003` between the push and the pull. The Action pushes one commit to
  `wave-003` while the run waits; a local commit made meanwhile would diverge from it, and `git pull
  --ff-only` (the wave's rule) would refuse. The run's own documents therefore stay uncommitted in the
  working tree until the pull is done, and the run's commit (made by the harness at the end, policy
  `run-unless-pushed`) comes last. The uncommitted documents do not block the pull because the Action's
  commit touches only `distribution/aws/`. Rejected: `git pull --rebase` or a merge (the wave says
  fast-forward only; a non-ff means something unexpected pushed to the branch, which is a stop).
- `DEC-4` Wait by polling, in the background. `gh run watch` or a `sleep` loop inside one foreground call
  would hit the 10 minute shell limit, so the wait is one background command that checks `gh run view <id>
  --json status,conclusion` every 60 seconds and exits when `status` is `completed`, and the run reads its
  output when notified. The poll gives up after 3 hours (wave 002's longest run took 1 h 23 min and its longest
  successful one 1 h 19 min). A run still `in_progress` then is not cancelled (cancelling is outside
  the authorisation) and not re-dispatched (two runs would race on the ref): the run stops `blocked`, naming the
  run id. Rejected: substituting a local
  Podman render (the wave forbids it).
- `DEC-5` Failure policy, copied from the wave's Autonomy Contract and made decidable here:
  first, a failure whose cause is the runner or the network (a failed `actions/checkout`, a runner lost, a
  rate limit, a registry pull error of the `plantuml-generator` image, a job that never reached `npm run
  generate:workdir` or `plantuml-generator`) is re-dispatched once, unchanged, without any push. Second, a
  failure whose log points at a file this wave changed or owns (`source/generator/workdir/**`,
  `source/library/packages/aws/**`, `scripts/resolve-aws-icons.mjs`) reopens the owning P1 run (W-1 for the
  validation, W-2 for the archive, W-3 for the AWS files): the fix is committed on `wave-003`, pushed
  (a fast-forward) and dispatched once. Third, anything else, or a second failed render: record the run id,
  the failing job and the log excerpt in `prg-003` and the run document, leave this run `in-progress`
  with the tasks after the failure marked blocked, and stop; this is the only point at which the wave asks
  for a human. A failed run pushes nothing (`push-distribution` is skipped), so the tree is as it was.
  `push-distribution` being the failing job (its push rejected) is the third branch: something else wrote to
  `wave-003`. Never more than two dispatches, so a render that fails twice is not tried a third time
  however the cause is classified.
- `DEC-6` The wave row's exit evidence "the pushed tip differs from the pre-wave tree only under
  `distribution/aws/`" is read as the gate's criterion, scoped to `distribution`, plus `AC-5`'s second
  check. Read literally and unscoped it is false by construction (W-1 to W-3 changed `source/`, `test/`,
  `scripts/` and `doc/`). The gate criterion wins; the second check makes it stronger, since it isolates
  the Action's own commit.
- `DEC-7` Do not look inside the 9851 files. The verification reads the paths from `git diff --name-only`
  and the nine stereotypes and 45 blocks from `bootstrap.puml`; it does not diff the PNG or `.puml` content
  of examples, which the Action regenerates and which can legitimately change bytes (the `eip` refresh
  commit of 2026-08-01 changed three PNGs with no source change).
