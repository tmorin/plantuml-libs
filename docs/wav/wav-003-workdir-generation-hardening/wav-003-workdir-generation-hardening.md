# Wave 003 — Workdir Generation Hardening

## Purpose

When this wave is done, `npm run generate:workdir` rejects a package whose
declared example template is missing or whose `icon_reference` resolves to
no icon of the generated library, a cached archive is only ever a complete,
valid, fully extracted zip, every family the AWS package produces has a
colour row, `scripts/resolve-aws-icons.mjs` reports the identifiers the AWS
upgrade how-to tells the maintainer to use, and the committed
`distribution/aws` carries those colours because it was regenerated by the
`package-builder.yaml` GitHub Action.

## Non-Goals

- Does not correct the stale statements in wav-002's plan (`Build` has a
  condition, the P2 concurrent-safe verdict ignores `push-distribution`,
  W-1's risk note). wav-002 is `completed` and its `prg-002` already records
  each statement as stale in Findings; rewriting a closed plan trades an
  accurate history for a tidier one. Left to the human: say so if an erratum
  is wanted.
- Does not regenerate `distribution/` for any package other than AWS, and
  never regenerates it anywhere but on GitHub: a distribution render takes
  hours of CPU, so it is done only by the `package-builder.yaml`
  `workflow_dispatch` Action, never by a local Podman run (W-4 is the only
  run that touches `distribution/`).
- Does not decide whether to add Google's redesigned, smaller icon set as a
  module; still a human or ADR decision.
- Does not run `npm run release`, create a tag, or push to `master`.
- Does not rebuild any package under Podman. Verification stays on
  `generate:workdir` (TypeScript only, no container) and, where a full
  render is wanted, on GitHub CI or `eip`.
- Does not re-pin any package version.

## Decision Prerequisites

- **Standing authorisation to push and dispatch (gates P2).**
  `package-builder.yaml` builds the *remote* ref, and its last job commits
  and pushes the regenerated `distribution/` to the ref it was dispatched
  on. So W-4 needs P1's work pushed to branch `wave-003` and workflow
  dispatches on it. These are outward-facing, and wave 002 stopped at
  exactly this point for want of a recorded go. For this wave to run with no
  human in the loop, the human gives the authorisation once, in chat,
  before `complete-wave` starts, and the orchestrator copies its words and
  date into `prg-003`. It covers: creating and pushing branch `wave-003`
  (and nothing else), and dispatching `package-builder.yaml` with
  `pkgName=aws` on that branch, at most twice (see the failure policy). It
  does not cover `master`, tags, `npm run release`, other packages, or any
  other workflow. No authorisation recorded in `prg-003` means P2 does not
  start and the wave stops after P1, stating why.

## Autonomy Contract

What `complete-wave` does end to end with no human step, so that nothing
below needs a decision at run time:

1. **Branch first.** Before W-1, create branch `wave-003` from `master`
   (tip `e95e177e2b`) and check it out. Every run commits there, never on
   `master` (wave 002's runs 0008 and 0009 committed on `master` and had to
   be moved).
2. **P1 is local.** W-1 to W-3 run one after another and commit on
   `wave-003`; each verifies with `generate:workdir -w <scratch dir>`, lint
   and `npm test`. No push, no Podman.
3. **P2 starts after the P1 gate.** Push `wave-003`, dispatch
   `package-builder.yaml` once (`gh workflow run package-builder.yaml --ref
   wave-003 -f pkgName=aws`), wait for the run to end, then `git pull
   --ff-only` the commit its `push-distribution` job made.
4. **Failure policy for the render, two attempts at most.**
   - Transient failure (runner error, network, rate limit, the job never
     reached the render): re-dispatch once, unchanged.
   - Failure whose log points at a file this wave changed or owns
     (`source/generator/workdir/**`, `source/library/packages/aws/**`,
     `scripts/resolve-aws-icons.mjs`): reopen the owning P1 run, fix and
     commit it, push, re-dispatch once. This is what wave 002 did for
     `groups.csv`.
   - Anything else, or a second failure: set W-4 `blocked` with the run id,
     the failing job and the log excerpt in `prg-003`, and stop. This is the
     only point at which the wave asks for a human.
5. **The wave ends unmerged.** Completion leaves `wave-003` pushed with
   `distribution/aws` regenerated. Merging into `master`, `npm run release`
   and any tag are the human's, after the wave is `completed`; they are not
   steps of this wave and nothing waits for them.

## Open Questions

- `resolve-aws-icons.mjs` was reported to resolve `Icon-package_01302026`
  while the repository is pinned to `07312026`. W-3 investigates and records
  the cause (fixture, stale page, or a script defect); it does not assume
  one.

## Risks

- W-1's check runs for every package. A rule that is too strict fails
  Azure, GCP, Font Awesome or Simple Icons, whose archives are not under this
  wave's control. The gate's all-package `generate:workdir` run is the
  check, and it was measured passing on the starting repository.
- W-1 and W-2 share `source/generator/workdir/`. They run sequentially in
  one worktree, so there is no concurrent edit; W-2 must not reformat
  `archive.ts` beyond its change, to keep W-1's diff readable.
- A render failure on CI (as happened in wave 002 with a stale
  `groups.csv` reference) leaves W-4 blocked after P1 is closed. W-1's check
  is meant to catch that class earlier; if it does not, W-4 records the
  cause and the fix goes into a reopened P1 run, as wave 002 did.
- `package-builder.yaml`'s `push-distribution` job deletes `distribution/`
  and restores its own artifact, so two dispatches on one ref race. W-4
  dispatches exactly once.
- The render is on GitHub's runners and takes a long time; the run waits
  for it and never substitutes a local Podman build.
- `continuous-integration.yaml` only triggers on pushes to `master`, tags and pull requests, so pushing `wave-003` starts no CI run; only the dispatched `package-builder.yaml` runs.

## Completion Criteria

The six P1 criteria and the four P2 criteria hold, each run's status file
reads `completed`, and the work sits on branch `wave-003`, not merged into
`master` and untagged, until the human decides.
